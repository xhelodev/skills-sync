# Self-hosting a service behind a tailnet gateway

Use when the user wants a service running on their VPS and reachable the way the others are — over Tailscale, never on the public IP — and listed in the service index. Covers the gateway's shape, the add-a-service procedure, and the boot and secret pitfalls that cost time.

## When to Use

- Installing anything new on the user's VPS (a web UI, an observability backend, a database front end), or being asked "¿cómo lo levanto en el VPS?".
- The user asks whether a port has to be exposed publicly so their apps can send data.
- The user wants to show something to someone outside the tailnet for a while — a demo, a review, a call — so the service needs a temporary public URL that vanishes afterwards.
- Adding an entry to the service index, or a new vhost to the gateway.
- Something on the host changed — containers, images or volumes — with no command of yours to explain it.

Not for: hardening the box (see `linux-server-security-audit`) or choosing *which* observability backend to run (see `opentelemetry-observability-backends`).

## Always-on rules

1. **Nothing new on the public IP.** Bind UIs to `127.0.0.1` and terminate TLS in the gateway, or bind straight to the tailnet IP. After every install run `ss -tln` and confirm no new `0.0.0.0` / `[::]` listener appeared; SSH should stay the only public one.
2. **Answer the "do I need a public port?" question directly** — usually no. Emitters that are tailnet members reach the service's tailnet IP with WireGuard in front, so no port is exposed and no TLS is needed at the ingest layer. A public port is only needed for emitters that cannot join the tailnet (a Vercel-hosted app, a cloud worker, a mobile app in the wild) — and there "behind nginx" is **not** an answer: the gateway binds only the tailnet IP, so adding a vhost exposes nothing to the Internet. The two real options are (a) put Tailscale on that emitter, tag it, and allow that tag to the single port it needs in the ACL (preferred: no bandwidth ceiling, no public surface), or (b) publish one path prefix through a tunnel whose connector is outbound-only — either a Cloudflare Tunnel (`cloudflared.service`, token-managed, ingress path regex → a vhost bound to `127.0.0.1`, as `otel.carpincho.dev` → `127.0.0.1:8446` does) or Tailscale Funnel. Never bind the service, or a new nginx vhost, to the public IP. See `references/funnel-and-serve.md` and `references/cloudflare-tunnel-publishing.md`.
3. **Inspect the host before planning instead of asking for specs.** `nproc`, `free -h`, `df -h /`, `docker ps`, `ss -tln`, `systemctl list-timers`, tailnet status. Ask only the decisions that are genuinely the user's: retention, purging their data, and account credentials.
4. **Never create the first account or invent a password** for the service you install. Install it, verify everything that needs no login, then hand over the register URL *and* the reason it matters — several stacks stay half-configured until the first organisation exists.
5. **Never delete the user's containers, images or volumes to make room**, not even ones you flagged as reclaimable. List what would be freed and let them decide: named volumes hold their databases, and "unused" is not "unwanted".
6. **When the host changed without your command, attribute it before debugging it.** `sudo journalctl --since "<time>" | grep COMMAND=` names the user and the exact command; other agent processes on the same box run privileged commands too, and guessing wastes a lot of time.
7. **Long plans ship as a file, not a wall of chat.** Under a plan-mode request the deliverable goes where the runtime says — `.hermes/plans/YYYY-MM-DD_HHMMSS-<slug>.md` — and the chat message stays at the verdict, the risks and the decisions you need; otherwise write a working doc in the app directory and deliver it with a `MEDIA:` line. When the user says not to act until told, the read-only inspection is the whole deliverable for that turn. **When the world moved since an earlier plan, write a new file that names what it supersedes instead of silently editing the old one** (a stack since uninstalled, a port now free): a stale plan re-read weeks later is wrong guidance with no warning attached.

## Procedure (adding a service)

1. Plan, get the go-ahead, then pick the home: `/home/debian/app/<service>` alongside `home`, `nextcloud`, `catcore`, `signoz`.
2. Install with containers and pin the image by **digest**, not by tag (`docker manifest inspect <repo>:<tag>`, take the `linux/amd64` entry's digest, write `<repo>@sha256:…` into the compose) — a tag floats, and `:latest` on a young project turns an unattended restart into a different application. Keep the compose file inside that directory so the deployment is reproducible.
3. Cap resources *before* the first start: `mem_limit` per service **plus the app's own memory variable**, and a retention setting for anything that stores telemetry. The app variable is not optional: engines like DuckDB and ClickHouse size their budget from the RAM they can see (the host, not the cgroup), so a capped container whose engine is uncapped is the one configuration that reliably gets OOM-killed under ingest — set the app variable to roughly half the `mem_limit` (`mem_limit: 2g` with `DUCKDB_MEMORY_LIMIT: 1GB`).
4. Bind ports: loopback for UIs, the tailnet IP for receivers — and spell the host part out (`- "127.0.0.1:5080:80"`). A bare `- "5080:80"` publishes on `0.0.0.0` and quietly breaks the no-public-listener invariant; confirm with `ss -tln | grep <port>` that the address reads `127.0.0.1`, not `0.0.0.0`.
5. Verify locally before touching the gateway: `curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:<port>/` and the health endpoint.
6. Publish it: hoy el patrón preferido es un **sidecar Tailscale** (`ts-<servicio>`, como adguard/traceway/hermes/livesync/mate-tv) o, si aplica, un `server` block en `/home/debian/app/home/nginx.conf` (que hoy solo atiende 80, 443 y 127.0.0.1:8446 — **8080/8081 son de mate-tv** y 8443/8445 ya no existen). Prefer `proxy_set_header Host $http_host` over `$host` when the service builds absolute URLs, so redirects keep the `:<port>` the user typed. **Before editing, record the current status code of every published endpoint** (gateway y nodos sidecar) and re-check after the rebuild. A `302` (redirect to the app's login), a `401` (API with no key) and a `404` (API root) are correct baselines, not failures — pinned down beforehand they are the regression test; guessed afterwards they read as damage.
7. Add the card in `/home/debian/app/home/src/data/services.ts`: `name`, `description`, `href: "https://{host}:<port>"`, `badge`, `icon`, `color`, `external: true`. The page script substitutes `{host}` at runtime, so the card works from any tailnet device.
8. Verify through the gateway, not only locally: `curl -sS --resolve <ts-hostname>:<port>:<tailnet-ip> https://<ts-hostname>:<port>/` — expect 200 and `ssl_verify_result` 0.
9. Confirm the index shows it, then write `README.md` in the app directory: ports, caps, `.env` location, update and backup commands, and what is still pending.

## Temporary public URL for a demo

When the ask is "muéstralo a alguien de fuera un rato", not a permanent ingest path, the shape is a Cloudflare **quick tunnel**: `cloudflared` run as your own foreground process (no token, no account, no DNS record) that dials out to the edge. Full recipe and limits in `references/cloudflare-tunnel-publishing.md`.

1. **Look at what `cloudflared` is already doing before starting anything:** `pgrep -af cloudflared`. A token-managed service (`cloudflared --no-autoupdate tunnel run --token-file …`) is a different tunnel on the same box serving someone else's hostname — any later pattern kill takes it down too.
2. **Prove the app enforces its own auth before exposing it:** the protected API routes must return `401`/`403` without credentials and `/login` `200`. A quick tunnel has no allowlist, no rate limit and no Access policy — the app's login is the only wall, and that is what you tell the user instead of calling it protected.
3. **Point it straight at loopback** so nothing depends on the gateway or its self-signed cert: `nohup cloudflared tunnel --url http://127.0.0.1:<port> --no-autoupdate > cloudflared.log 2>&1 &`, then `grep -oE 'https://[a-z0-9-]+\.trycloudflare\.com' cloudflared.log | head -1` after ~10 s.
4. **Verify through the edge, not "tunnel registered":** public root returns `200` with the app's `<title>`, and a protected API route still answers `401`. That pair proves proxying works *and* auth was not bypassed. A few hundred ms per request is normal; the log's `INF Registered tunnel connection` is not evidence the origin is reachable.
5. **Hand over the ephemeral truth:** random subdomain, dies on process kill or reboot and cannot be recovered. Offer Basic Auth in front (a loopback nginx on a spare port between the tunnel and the app) when the demo will last or the link goes to outsiders, and a named tunnel + Access when it needs to be permanent.
6. **Tear down and prove it:** kill the PID, then re-request the URL and expect **530** (edge has no connector). `pgrep` coming back empty is not proof.

## Pitfalls

- **The gateway's `nginx.conf` is baked into the image.** Editing the file changes nothing until the image is rebuilt (`cd /home/debian/app/home && ./build.sh`). Validate first with `docker run --rm -v nginx.conf:/etc/nginx/conf.d/default.conf:ro -v certs:/etc/nginx/certs:ro nginx:alpine nginx -t`: the bind failure on the tailnet IP inside that throwaway container is expected, so read `syntax is ok` and ignore the rest. A bad config takes the index and every proxy down with it. After the rebuild, **prove the running config is the new one**: `docker exec <gateway-container> cat /etc/nginx/conf.d/default.conf | diff - /home/debian/app/home/nginx.conf` must print nothing. Never use the image timestamp as evidence — a Docker build-cache hit reuses the previous layer, so `docker image inspect … --format '{{.Created}}'` can show yesterday's date on an image that does contain today's file.
- **Compose reads `.env` from the directory of the compose file**, not from where you run it. A symlink has to be relative to *that* directory (`../../.env` from a generated `pours/deployment/`), and the failure is quiet: the variable resolves empty, the database container refuses to initialise, and every dependent service restarts in a loop.
- **Boot order matters when a container publishes on the tailnet IP.** If docker starts before `tailscaled`, the bind fails; add `/etc/systemd/system/docker.service.d/tailscale.conf` with `Wants=tailscaled.service` and `After=tailscaled.service`, then `systemctl daemon-reload`. `restart: unless-stopped` covers the gap in the meantime.
- **Tool output masks secrets, files do not.** A real password read back through a tool can appear as `***`; do not try to repair that string. Patch around it with a regex or set the value deliberately, and keep the real secret in a `chmod 600` `.env`.
- **Check ports before choosing one**, and check them twice: a number can be free on the host and already taken inside the compose network.
- **A generated deployment directory stops being the source of truth the moment you edit it.** If the generator can run again, record your manual edits (limits, binds, retention) in the README or they vanish on the next generate.
- **Don't install into a disk you have not measured.** A stack with ClickHouse plus Postgres wants tens of GB of headroom; check `df -h /` and `docker system df` first and say plainly when the box is tight.
- **A proxy in front of a loopback-bound service adds reachability, not authentication.** The app decides whether auth applies from *its own* bind address, so a service that believes it is private on `127.0.0.1` stays auth-free once the gateway republishes it — and if it inlines a session token in its HTML (Hermes' dashboard does), any tailnet device can read that credential and use the whole API. Before telling the user a proxied service is protected, `curl` its `/api/*` routes through the gateway; if it should require auth, configure the app's own provider (password/OAuth/token) rather than trusting the network.
- **An app behind the gateway sees the proxy's IP, not the client's.** Anything that rate-limits, blocks or audits per client IP (OTLP receivers, APM backends, most APIs) needs the proxy's range declared trusted — e.g. `TRUSTED_PROXIES: "172.16.0.0/12"` with `TRUSTED_PROXY_HEADER: "X-Real-IP"` — *and* the vhost must actually set `X-Real-IP $remote_addr`. Skip it and every tailnet sender collapses into one rate-limit bucket, which surfaces later as unexplained throttling rather than as an error.
- **A public prefix is a two-control-plane change, and a status code alone will not tell you which plane answered.** The ingress path regex lives in the Cloudflare dashboard — for a token-managed tunnel there is *no* config on disk, so read the live rules out of `sudo journalctl -u cloudflared | grep 'Updated to new configuration'` — while the allowlist lives in the gateway's loopback vhost. A `$`-anchored regex is the classic mistake: it matches only the bare path and hands every subpath to the catch-all, which from outside looks exactly like a correct deploy that has not been wired up yet. Apply nginx first (the stale ingress path then 404s at nginx, harmless while nothing calls it), then the dashboard, and say plainly that the public path stays 404 until the second half lands. To prove a request reached the origin, diff the public response against the loopback one header-for-header: `cloudflared`'s catch-all `http_status:404` answers with an empty body and no `content-type`, nginx and the app answer with both. See `references/cloudflare-tunnel-publishing.md`.
- **`pkill -f '<something> tunnel'` kills the shell that runs it.** The pattern matches the tool call's own command line, so the call dies with signal 15 and empty output — that reads like a crashed command, not a successful kill. Use the exact name (`pkill -x cloudflared`) or a PID from `pgrep -af`, and when a battery of checks returns nothing, re-run only the checks: the kill already landed.
- **On this host the `*.ts.net` FQDNs do not resolve from the VPS itself** (Tailscale DNS / `accept-dns` is off), so `curl https://<host>:<port>/` fails with `Could not resolve host` and looks like the service is down. Use `curl --resolve <host>:<port>:<tailnet-ip> https://<host>:<port>/`, which also sends the right SNI; other tailnet devices resolve it normally. Confirm with `tailscale status` (node name + `100.x` IP) rather than assuming DNS is broken at the service.
